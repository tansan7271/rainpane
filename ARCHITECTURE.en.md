# How Rainpane works

[한국어](ARCHITECTURE.md)

This is an English translation of [ARCHITECTURE.md](ARCHITECTURE.md). The Korean version is the original. If the two differ, follow the Korean version.

This is a menu bar app that makes rain fall over macOS windows. Claude Code wrote all of the code. This document is a set of design notes written while building it.

## Build and run

```sh
./build.sh        # creates build/Rainpane.app (signed with the self-signed certificate if there is one, otherwise ad-hoc)
./build.sh run    # builds, then relaunches
./dev-restart.sh  # build → runtime shader compile check → restart only if it passes (use this after editing shaders)
RAINPANE_DEBUG=1 build/Rainpane.app/Contents/MacOS/Rainpane   # logs fps, CPU and GPU time, and poll count every second
```

- Even if `xcode-select` points to the Command Line Tools, `build.sh` selects Xcode through `DEVELOPER_DIR`.
- The Metal shaders live in `Shaders.swift` as a string and are compiled at runtime (there is no separate metallib).
- It uses `ObservableObject` instead of SwiftUI `@State`. This is because the macro plugin is not available when building with the Command Line Tools.
- With ad-hoc signing, the signature changes on every build. So you may have to grant **Accessibility permission** again after each rebuild. If you create a self-signed certificate once with `./setup-signing.sh`, the permission stays (the keychain password is random per computer, in `.signing/password`).
- On-screen text is written side by side as `L("한국어", "English")`. The default is English. A button at the top of the settings window switches the language (`language`).

## Coordinate system

- All simulation and shader data use **global Quartz coordinates**: the origin is the top-left of the main screen, y grows downward, and the unit is pt. This is the same coordinate system as `CGWindowList`, so no conversion is needed.
- Each per-screen renderer converts to local coordinates and NDC with the `screen` uniform (origin, size).
- Rain streaks are the only exception. They are generated in screen-local coordinates.

## Depth (occlusion)

1. The mask texture (RG8) is redrawn only when the window layout changes. Each pixel stores the rank of the frontmost window covering that position. R is the global rank (for water occlusion). G is **the rank among only the windows that overlap that display** (for rain). 0 is the front and 255 is the desktop. It also follows the window corner curves.
2. Each raindrop has a depth `d` (0 near to 1 far). A window's depth is `rank within display × depthStep`. A raindrop is visible only when `d < window depth`. So regardless of focus, the top window on each display has no rain, and windows further back show more of it.
3. Water elements (pooled water, streams, drops, water sheets) carry the rank of the window they belong to. They are drawn only when `mask rank >= own rank`, so they disappear naturally when a window in front covers them.

## Water simulation (`WaterSimulation`)

- **Pooled water**: each window has a 1D height array of cells about 4pt apart. A virtual pipe (shallow water) model runs in 120Hz substeps. Rain inflow goes only into cells not covered by a window in front. Acceleration while dragging a window acts as a horizontal pseudo-force (sloshing). When the level at either end goes over `poolCapacity`, the water overflows.
- **Inertia**: if a window moves down faster than gravity, the water stays in the air and falls freely. When it touches the top edge again, it is redistributed cell by cell. The part that ends up outside the window becomes a water sheet that continues at the speed it was falling (the starting time on the shader's fall curve is matched to that speed). If the landing speed is high, it splashes.
- **Streams**: the overflow rate is heavily smoothed, and turning on and off has hysteresis (without it, streams flicker and jitter). While water flows, the head moves down along the side. When the flow stops, the stream drains from the tail. When it flows again, it refills from the top. Drops fall from the bottom corner.
- **Corner joins**: pooled water and streams are both drawn by the outward distance from the window outline (a rounded rectangle). The pool shader handles the top corner arc. It narrows the arc so that its thickness equals the stream width at the end of the arc. So the two shaders meet without a seam. The arc is thickened to stream width only as far as the stream head has gone around the curve (`cornerReach`: the distance traveled down from the top edge, as a fraction of the arc angle; the fourth value in the pool data). When we thickened the whole arc at once, the end of the arc looked cut off horizontally until the stream had gone all the way around the curve (noticeable on widgets with large corners).
- **Widget water height**: on a short surface, water drains to both ends quickly and stays at the edge height (on a long window, the middle fills higher). Also, drops on window glass take water at the same frequency regardless of width. As a result, water pooled about 25% thinner on widgets than on windows. We left windows as they were. For widgets only, we scaled down the amount the drops take relative to a 400pt width, and raised the overflow height by 25%.
- **Drips**: they fall under gravity. If one hits the exposed top edge of a window below, it merges into that pool and splashes.
- **Drops on window glass**: they form at the top of the front window (optionally on all windows, or on all windows except the front one). They move down by stopping and sliding over and over, and leave small leftover drops behind. They take water from the pool.
- **Water sheet**: the leading edge (the main body) uses the same crisp lighting as the drops (`shadeDrop`). Edge darkness appears only near the outline, where the water is very thin. The dark line for light backgrounds is made as "copy highlight − original highlight" (`highlightShadow`), where the copy uses a slightly rotated light direction. So it sits next to the highlight with the same thickness. Building a ring from a range of highlight angles turns into thick gray smudges on gentle slopes. Setting the width with fwidth causes jagged edges. A bright highlight runs along the leading edge. Above it, faint copies shaped like the leading edge remain as marks (old leading edges left behind as the sheet moved down in fits and starts). They stay faint, and the gaps between them widen further up. Sparse thin vertical streams and a thin leftover film also remain. When a window disappears, it is judged "closed" if no Space switch and no simultaneous disappearance of several windows happens within 0.2s. Then a water sheet proportional to the amount of pooled water flows down, generated procedurally on the GPU (a thick head at the front, splitting into finger shapes).
- **Minimize**: if the size shrinks and no corner stays fixed (`looksSuckedIn`; when the user resizes a window, one corner stays in place), we treat it as starting to be sucked in. If it has the Genie shape (`looksLikeGenie`: same width, bottom corners in place, only the top edge moves down), a water sheet flows from the original position at that moment (`letGo`; the window is ignored with `goneSoon` until it disappears). Otherwise, the water is kept hidden at the original position (`frozen`). If the window then disappears, a sheet flows right away from the original position. If it is Mission Control, there is no sheet. If the window stops for 0.15s and is still there, the water shows again at its current position. In the Genie effect, the window slides sideways for the first two frames. From the third frame, the top edge comes down while the bottom corners stay, and it is also pushed sideways. So it is caught before the window moves down much (confirmed with recorded measurements). Before, it was treated as a window moving down fast, and the water was scattered as drops. So minimizing produced almost no sheet. Later, the sheet flowed only after the Genie effect finished. The water went into the Dock with the window and then popped out at the original position.
- **Hide (⌘H)**: when all of an app's windows disappear at once, this used to be treated as a Space switch and the water was stored. Now, as soon as `didHideApplicationNotification` arrives, the water on that app's windows flows away as a water sheet (`appHidden` → `letGo`). When we decided after the windows had disappeared, the water vanished with the windows and flowed down a few frames later.
- **Writing Tools windows are excluded**: for Apple Intelligence Writing Tools, the app itself opens a 280×168 transparent window next to the input field (what you see is a small icon). App and window properties cannot tell it apart from a dropdown, and the title is visible only with Screen Recording permission. So windows of this size (±3pt) are filtered out.
- **Mission Control and Show Desktop**: `WindowManager` opens a screen-sized window at layer 19 (Mission Control) or 18 (Show Desktop). While it is up, the window list is emptied and all windows are treated as "closed" immediately (the water just disappears, with no sheet). When it ends, water builds up again from zero. During this time, the window coordinates in CGWindowList change to the shrunken positions or to positions pushed off screen.
- Water on a window that moved to another Space is kept for 30 minutes.

## Rendering (`Renderer`, `Shaders`)

- **Rain streaks**: they have no state. Position, depth, and speed come from hashing the instance number and time. x is picked again every cycle to remove repeating patterns. The CPU cost is zero.
- **Splashes**: these are also computed without state. A position is picked from the list of exposed top-edge segments, in proportion to weighted length (the screen bottom has weight 0.25). Five drops fly out along parabolas.
- **Water shading**: a single `shadeWater()` draws all water elements.
  - Band- or bar-shaped water (top edges, side streams, pouring streams) curves in only one direction. So the highlight vector H is projected onto that curving axis. This way the highlight forms a line even with diagonal light.
  - The light is a point light outside the top-left of the screen (`lightAt`). Highlights get weaker with distance.
  - To stay visible on light backgrounds (Light Mode), the body is not darkened. Instead, a thin, faint dark line sits next to the white highlight. On top edges, a dark line on the water surface side and a bright reflection line below it are drawn explicitly.
  - Drops on window glass, drips, and splashes are ball-shaped, so they use a separate function with a single directional light (`shadeDrop`). The user likes this look, so it stays as is.
  - Do not use `time × (a value that changes every frame)` as a phase in shaders. After the app has run for a long time, time gets large and the phase jumps every frame, which causes jitter. Flow speeds use fixed values.
  - The smaller the water's pixel width (`featurePx`), the more the normals and highlights are smoothed. This prevents specular aliasing that makes thin streams jitter.
  - The cross-section of a side stream is asymmetric. The window side, where the water clings wetly to the glass, is gentle (−0.4). The outer free surface is steep (+0.9). With a symmetric half-cylinder, both sides turn dark and it looks like a double-line border.
- All output uses premultiplied alpha.
- It uses 3-slot ring buffers and a non-blocking semaphore. If the GPU is behind, that frame is skipped and the main thread is not blocked.
- It does not use Screen Recording permission. There used to be a refraction mode that captured the screen behind the water and made it look bent. The difference was small compared to the burden of the permission, so we removed it (we also deleted the refraction branch in the shader, and 25 fixed-seed snapshots were byte-identical before and after).

## Performance notes (measured on an M1 Pro with two 4K displays)

- **Most of the load is WindowServer compositing**. A transparent full-screen layer costs something on every refresh, **even when it presents an empty frame**. At 60fps it was about +30%p of WindowServer per screen. Shader cost (GPU 0.7~3ms) and simulation (about 2% of the main thread) are secondary.
- So the key to saving is "fewer refreshes".
  - The default is always max FPS (60). The user chose this, saying there is headroom. It drops to 30fps only on battery, in Low Power Mode, or under thermal throttling (`thermalState >= .serious`).
  - Optional "Adaptive": 30fps normally, max FPS only while windows move or while there is a water sheet or water in the air
  - When rain is 0 and the water is still, the display link stops completely and only window changes are watched at 4Hz
  - When a full-screen app covers a screen, that screen is not drawn
- Changing the render resolution or color space barely changed the WindowServer load.
- The CPU figure at the bottom of the settings is the CPU usage of the whole app (same unit as Activity Monitor, 100% = one core, from `getrusage` every second). While it rains it is normally about 17%. Most of that is not our computation but the system cost of presenting a transparent full screen at 60fps. It used to show the wall-clock time of one tick (ms) without a unit, which was confusing. That value (tick in the debug log) includes waiting on `nextDrawable` (about 57% of main thread samples). The largest real CPU cost in our code is reading the window list (`CGWindowListCopyWindowInfo`, about 1.2ms per call on a real machine: 12Hz normally, every frame while windows move).
- Measuring: `RAINPANE_BENCH=1 build/Rainpane.app/Contents/MacOS/Rainpane`. It measures window list reads, per-stage CPU and GPU with 40 fake windows moving and at rest, GPU components (rain, water, splashes), and closing all at once (water sheets). The scene is the same every time (fixed seed), so before and after can be compared. If you do other work, the GPU clock changes and the numbers swing a lot. To check that the look is unchanged, shoot the same scene with `RAINPANE_SNAPSHOT_SEED=7` and compare pixels.
- Second round of optimization (same look): the bottom of the sheet rectangle extends only as far as the leading edge can reach right now. When sheet thickness is sampled three times in one pixel, the vertical streak value (noise) is shared (sheet GPU about 20%↓). In the occlusion calculation, the front windows that cross a top edge are picked out first (sync about 4×↓). The window list is read directly from CF values instead of being converted to a Swift dictionary. Environment variables are read only once (reading them every frame took 7% of the main thread). Windows that disappear all at once for Mission Control or Show Desktop do not shed a water sheet (with many windows, dozens of sheets used up a whole GPU frame. At first we kept it only for the top window on each display, then removed that too).
- Room to cut further: switch to `CAMetalDisplayLink`, 24fps when rain is light, stop each screen separately when it has no activity.

## Desktop widgets

- Widgets are small windows that the Notification Center process shows at desktop level. The window list gives the exact position and size of each widget. They are ranked behind all windows. So water pools and flows on them the same way as on normal windows, and it is hidden along with them when a window in front covers them.
- Rain shows fully over widgets, as on the desktop (rank within display in the mask = 254).
- No water is put on the Dock or notification banners. We tried raising the overlay above them (level 22) and reading their positions with the Accessibility API. But it needed the permission, and it was hard to follow the Dock's shrinking size exactly. It also had a side effect: streams from other windows near the Dock got cut off. So we reverted it. The overlay now sits just above normal windows (level 1), so the Dock, notifications, floating panels, and menus naturally cover the rain and water.

## Displays and corners

- Every water element carries its **owning display** (the screen that contains the window's center), encoded together with its rank as `rank + 256 × screen`. The shader discards it if it belongs to another display. So the stream of a window maximized on the left display does not show at the edge of the right display. Drips also land only on windows on the same display.
- Window corners are approximated with a **superellipse (squircle)**, not a circular arc (`cornerDist`). The exponent is n = 2 + 3 × `cornerSmoothness`, and the curve length is R × (1 + 0.5 × smoothness). The occlusion mask, pooled water, streams, and hanging drop positions all use the same curve.
- A stream ends at the 65° point of the bottom corner curve. The drop hanging there grows in proportion to the amount waiting to fall (`dripAcc`). When it is full, it falls **at the same position and size**. When the flow is strong, the amount needed for one drop gets smaller, so small drops fall quickly one after another. They stretch with speed and join up like a stream.
- Water on a top edge that becomes newly covered by a window in front turns into a water sheet at the front window's rank and is swept down (`computeExposure` → `sweepCovered`).
- When water in the air leaves the window and turns into a water sheet, `clipTop` sets the upper limit of the sheet. Water exists only over the length of the band that was falling, so the sheet does not suddenly get longer.

## Turning things on and off

At the top of the settings, under the master switch (`enabled`, same as right-clicking the menu bar icon), there are separate "Rain" (`rainEnabled`) and "Mouse drops" (`pressEffect`) toggles. When Rain is off, window tracking, water simulation, and drawing of the rain overlay all pause entirely (window changes do not wake them while idle), and only Mouse drops keep working.

## When taking screenshots

- The rain overlay window is a transparent window that covers the whole screen. So ⌘⇧4 → Space bar ("select a window") picked the rain overlay window instead of the app window (the capture showed only rain streaks on a white background). While the screenshot tool shows its screen-sized selection window (`WindowTracker.capturing`), the rain overlay window is lowered below normal windows (to desktop level) and draws nothing. The small preview that appears in the corner after a capture, and the toolbar, are filtered out by size.
  - To tell whether a selection is in progress, it looks only at the screen-sized selection window of `screencapture` (above layer 1000, measured at 1498). Both ⌘⇧4 and ⌘⇧5 show this window, and it disappears as soon as you capture or cancel. At first we matched screenshot tool windows broadly (`Screenshot` at layer 24 on the ⌘⇧5 toolbar side, and `screencapture` at layer 1000 for recording). Those two windows stayed up for the whole recording, and for about 5s after it ended. So the rain hid even with the recording setting off, and came back late. The name `screencaptureui` was a guess and never matched anything.
- While recording (`WindowTracker.recording`, setting "Hide rain while recording the screen", on by default): when recording starts, all screenshot tool windows disappear, and the system (`Window Server`) shows a 28×28 recording indicator window in the top-right corner of each display (measured). When this window exists, the rain overlay window is lowered. Mouse cursor windows on the same layer (2147483630), such as 42×60, are filtered out by size and position. We have not confirmed whether the same indicator appears when another app records, or when the microphone or camera is in use.
- The window is not hidden (`orderOut`). Only its level is lowered. The frame loop (display link) is attached to this window's view, so hiding it could stop the loop.
- While rain is off, the rain overlay window is also kept lowered (it drew nothing but still got picked by window selection).
- Clicks made while selecting, and while recording (if the setting is on), do not make drops (so they do not show up in the capture). While rain is off, the window list is not read, so it is checked once on each press.

## Pressing with the mouse (`PressEffect`)

It is modeled on the feel of the Galaxy S6 water drop lock screen. It looks like pressing a finger on water trapped between glass and plastic wrap. While you press, the area the water touches spreads. When you let go, it shrinks and disappears.

- Input: `NSEvent.addGlobalMonitorForEvents` receives only left button press and release (mouse events do not need Accessibility permission). While the button is held, it follows the cursor every frame with `NSEvent.mouseLocation`, and catches missed releases with `pressedMouseButtons`. When an event arrives, it calls `wake()` even when idle.
- Controls: the "Drops" tab in settings (`PressEffect.Tuning`, and `GlassTuning` for glass). Quick click size (25pt), max size (48pt), and spread and fade speed; stretch and wobble when dragging; small droplet count, size, distance, and neck length; shadow darkness and spread; glass refraction and blur. All numbers below are defaults (scale 1). The defaults are the values the user tuned in the tab. The shadow values go to the shader in the group data (p2.zw).
- Size: a spring follows the target radius. While pressed, it spreads fast at first (overshooting slightly), then slower and slower (time constant 0.33s), up to the max (48pt). If you let go before it reaches 90% of quick click size (25pt), as in a quick click, it finishes spreading to that point first. On release, it shrinks smoothly and disappears without wobbling (critically damped, ω 12). We also tried making it grow 10% and fade like a soap bubble. But SwiftUI `.opacity` has no effect on Liquid Glass (every glass layer in the container stays at opacity 1), so it vanished abruptly. We reverted it.
- The position sticks to the cursor directly. When we made it lag behind with a spring, a quick drag and stop left the drop stretched out while it caught up.
- Outline: always a smooth circle or ellipse. Dragging stretches it in the direction of motion (the target is proportional to speed and saturates with tanh, up to about 3:1). Stretch = a shape that follows the target directly with a first-order lag (22ms) + a 2Hz soft oscillator that gets kicked by however much the shape changed. If a single oscillator handles everything, the drop stays stretched for a moment when you stop and then comes back ("a one-beat pause"). Making it faster to reduce that makes the wobble too abrupt. Clamping hard at the upper limit builds up spring velocity and causes the same symptom. To keep the area the same, one axis is scaled by (1+e) and the other by 1/(1+e). Stretching with an outline mode like cos2θ pinches into a peanut shape at large stretch, so we use a true ellipse. Contact line noise and the k=3 and k=4 modes made the surface look rough, so we removed them.
- Pressing a drop again while it is shrinking makes that drop swell again (double click).
- Small droplets (`Satellite`): on press (after the main drop has spread for 0.07s) and on release (only if held for 0.4s or more: bursting twice even on a quick click looks like too much), they fly out evenly from just inside the main drop's edge. Their size is 7% to 30% of the max radius, and small ones are much more common. Regardless of the cursor, they spread outward with a strong ease-out (5th order) and nearly stop. Toward the end of their lifetime (0.5~0.8s) they shrink faster and faster and disappear. They stop at about the neck length (k) from the main drop's edge, so the neck stretching and breaking stays visible for a long time (when we flung them far and fast with friction, the neck broke within one or two frames and was barely visible). Small droplets also merge with each other when close. They merge with the main drop by a smooth union (smin, merge distance k = 20% of the max radius). So when close they are joined by a neck, and as they move apart the neck thins toward the contact point and breaks. Firing them from the center, or right at the moment of pressing, made them stick to the spreading main drop and look lumpy, or left only dots with no neck. So they are fired a little later, from the edge the drop is about to spread to.
- Scroll dust (`pressScrollDust`, off by default: after trying it, it was too much to leave on): scrolling is also a mouse event, so it arrives without any permission. With no main drop, small droplets scatter from around the cursor (±26pt horizontally) in the direction the content moves (±0.4rad). One is made for every 18~32pt scrolled (at most 40 per second). The larger a single scroll, the farther they fly (10~90pt). A wheel mouse scrolls in lines, so the amount is multiplied by 12 to match pt. Small droplets without a main drop are each drawn in Metal as their own small group.
- Keyboard (`keyboardPress`, off by default, `KeyboardFocus`): other apps' key input and focus position are available only with Accessibility permission (it asks for the permission only when turned on, and checks every second whether it has been granted). Queries are IPC to another app, so they run on a background queue with a 0.2s limit. Electron (VSCode, Slack) and Chrome do not build an accessibility tree by default, so `AXManualAccessibility` is turned on for the app that comes to the front (VSCode may take us for a screen reader and switch to "Screen Reader Optimized"). Apps that already had it on are left alone. When the feature is turned off, only the apps we turned it on for are reverted.
  - Tab: a quick click drop appears only if, 0.08s later, focus has moved to another field (or to a different spot in the same field). Tabs handled inside a field, like indentation in an editor, are filtered out. The comparison is with the last field seen. The drop appears at the text cursor position (`AXSelectedTextRange` → `AXBoundsForRange`, length 0 → right edge of the previous character → left edge of the next character). If there is none, it appears at the center of the focused element (ignored if larger than 700×300).
  - Return as "send/press": it does not read the text in the field (only the field type, position, and size). Non-text elements such as buttons and links, password fields, and single-line fields (`AXTextField`, `AXComboBox`, search fields: address bars, search boxes) always pop droplets. Multi-line fields (`AXTextArea`: chat boxes, notes, email bodies, etc.) also always pop droplets, except for Shift+Return or Option+Return (a line break in chat), code editors (`AXRoleDescription` containing "editor": the VSCode editor), and hidden input fields narrower than 80pt. So droplets also pop on line breaks in notes and email bodies (a tradeoff the user chose).
  - What we ran into: at first, every Return put a quick click drop at the cursor position. It appeared on every line break, and in the middle of chat boxes. Next, we filtered out line breaks in multi-line fields with the rule "if the text before Return soon disappears, it was sent" (the text was reduced to a character count and hash as soon as it was read. In VSCode chat, even an empty field returns placeholder text as its value, so "is it empty?" or "is the cursor at the start?" did not work). It was accurate, but reading the input even briefly felt wrong, so we removed it. The Safari address bar and the Google search box are caught by the single-line field rule. On this macOS, NSLog does not end up in the unified log (if you need diagnostics, write to a file. In zsh, `log` is a builtin, so use `/usr/bin/log`).
  - Passwords: in a password field (`AXSecureTextField`), or while the system is in secure input mode (`IsSecureEventInputEnabled`, which browser password fields also turn on), it does not even ask for the text cursor position (that would reveal the password length). Return there is always a submit, so droplets pop right away from the field edges. Tab puts the drop at the center of the field.
  - At first there was only the multi-line field rule, so nothing popped in the Safari address bar or the Google search box (after Return, the text stays or focus moves to the page).
  - `pop(rect:)`: with no main drop, small droplets (radius 3~15pt, smaller ones more common) fly 8~50pt outward (diagonally at corners) from 11~19 random spots on the field edge. Each small droplet puffs out quickly during the first 0.05s. We tried showing a main drop shaped like the input field (shrinking into a circle, fading quickly, scattering into drops that filled the field), but every way of making it disappear looked unnatural.
- Group drawing (Metal): the main drop and the small droplets near it (within 2k, the distance where a neck can form) are bundled into one group and drawn in one rectangle. Small droplets that are far away are each drawn as their own small group with no main drop (if you drag the main drop far away after the droplets burst, the group rectangle gets needlessly large). The signed distance is the smin over the whole group, and normals come from central differences. The meniscus width follows the size of the nearest drop, so a small droplet looks like a fully round drop. The main drop stays until all of its small droplets are gone.
- Group drawing (glass): small droplets are also circles in the same `GlassEffectContainer` (spacing 20), so the system joins and separates them like liquid. The glass in a container merges into one layer, and the lens strength (`inputInnerRefractionAmount`, `Height`) is set from the smallest shape. So while small droplets exist, the main drop turns transparent with only a thin outline left. We set the values again with the same formula as for a single shape (−1.3r, min(0.72r, 20)), where r is the radius of the largest drop.
- We also tried leaving drops at the trailing edge while dragging (a trail line, then just three or four beads coming off). It did not look good, so we removed it. A different effect is planned for dragging.
- Drawing (`pressFragment`): the inside is flat, thin water. Only the meniscus at the edge has normals tilting outward. `shadeDrop` + a dark line next to the highlight + a faint water-colored film. This happens on the surface of the screen, so it is drawn without the occlusion mask.
- Where it is drawn (`PressOverlay`): not in the rain and water overlay (just above normal windows), but in a separate screen-saver-level window per screen. So it shows in front of the Dock and menu bar. It is shown only while pressing, and hidden after presenting an empty frame. Metal drops are drawn by reusing `ScreenRenderer` with an empty snapshot.
- We tried shading the outer area, where the wrap is pressed into a dent. It looked like a gray shadow smudge, so we removed it (the directional shading spread out too wide).
- Instead, to stay visible on light backgrounds, a subtle shadow is laid just outside the outline (`pressShadowFragment`: the smin shape of the whole group, offset 4pt down, blurred wide (52% of the nearest drop's radius, 3~21pt), empty inside the drop, max alpha 0.15. Small droplets get a narrower, fainter shadow. If it were just as wide, it would look like a halo). In glass mode too, only this shadow is drawn with Metal under the glass. The Liquid Glass filter has `inputShadow*` values, but opacity is 0 for both clear and regular, and there is no separate shadow layer, so we could not use them.
- Liquid Glass material (`pressGlass`): a full-screen `NSHostingView` sits on top of the overlay window's Metal view, and it draws `.glassEffect(.clear, in: TiltedEllipse)` for each drop. `NSGlassEffectView` only supports rounded rectangles, so we use SwiftUI, which can use a rotated ellipse. WindowServer composites the refraction of the screen behind, so no Screen Recording permission is needed. When this is on, the Metal drops are not drawn. The snapshot tool cannot reproduce it (the system composites it).
  - Fully clear: the public API has no blur control, so we change the system glass filter values directly. In the `glassBackground` filter of the glass layer (`CABackdropLayer`), `inputBlurRadius` and `inputBlurOpacity0~3` are set to 0. For the hazy film (`inputFaceColorMatrixWhite` 0.8 / `Black` 0.05 / 5% white `FillColor`), the white film is turned off (made transparent). Only its brightness range is kept, as much as "Visibility on light backgrounds" (`pressGlassLightBG` 0.25 → White 0.95) and "Visibility on dark backgrounds" (`pressGlassDarkBG` 1 → Black 0.1) ask for. The `gaussianBlur` (radius 30) of the window's top-level "capture backdrop" is also set to 0. The glass `CABackdropLayer` captures the screen behind at half resolution (`scale` 0.5), so with blur off the inside looks fuzzy. We raise it to 1. Narrowing the brightness range makes white backgrounds look gray and black backgrounds look lifted, so drops stay visible even on plain backgrounds (a fixed color tint gets lost on one of the two, light or dark backgrounds). Narrowing both sides by the same ratio is too strong on light backgrounds and invisible on dark ones, so the two sides are set separately. Only values in the same filter change, so there is no extra cost. SwiftUI puts the values back whenever the shape changes. So on every update we apply the change immediately with `layoutSubtreeIfNeeded()` and then overwrite the values. This relies on a private implementation, so the glass may go back to the default when macOS changes. The filter also has values like `inputAberration*` (chromatic aberration) and refraction strength (`inputInnerRefractionAmount` −52, `Height` 20).

## Switching desktops together across displays (`SpaceSync`)

When "Displays have separate Spaces" is on, macOS switches desktops separately on each display. Turning it off makes window snapping and the menu bar awkward. So we leave it on and make the displays switch together, like Windows virtual desktops. This is turned on and off separately from the rain effect (`spaceSync`, off by default, "Desktops" tab in settings). It asks for Accessibility permission only when turned on.

- Detection: when `activeSpaceDidChangeNotification` arrives, it reads each display's desktop list and current desktop with SkyLight's `SLSCopyManagedDisplaySpaces` (private, read only). Type 0 is a normal desktop, and type 4 is a full-screen app. If only one display changed since last time, the others follow that display.
- Switching: it presses the macOS "Switch to Desktop N" shortcut (118 + N − 1 in `com.apple.symbolichotkeys`, Ctrl+number by default) on the user's behalf with `CGEvent`. N is a number that runs across all displays (display order is the `SLSCopyManagedDisplaySpaces` order; N = number of normal desktops on the earlier displays + index + 1). The shortcut must be turned on in System Settings. Numbers that were never turned on (the ones created when you add a new desktop) are off by default. So the "Turn on these shortcuts" button in the settings window turns them on as Ctrl+number (it writes the plist and has it reloaded with `activateSettings -u`, up to 10). Other shortcut entries are left as they are, and if the values read are not in the expected shape, nothing is written. If the key value is "no key" (65535) or out of range, it does not press it. Switching directly with `SLSManagedDisplaySetCurrentSpace` gets out of sync with the state the Dock knows, so it is not used.
- Changes on a display that is being switched (`pending`) are not treated as switches by the user (this prevents ping-pong, where the displays keep following and undoing each other). Arrival is checked by polling every 0.05s: when switching to an empty desktop, focus does not move, so no notification arrives. Then the old state stayed and the wrong display got followed. If the user switches again during a switch, things are realigned after the switch finishes. If a switch does not happen within 1.2s, the settings window shows a notice, and that number is not pressed again until the configuration changes or the shortcut is turned on (if the system does not take the shortcut, Ctrl+number is typed into the front app as is). If the display being switched is removed, the pending switch is dropped. If two displays change at once, there is no way to know which came first, so nothing is touched.
- Switching with the shortcut moves focus to that display. So after the switch finishes, the originally focused window is raised again through the Accessibility API (window titles and contents are not read). If that window is not on screen (when the switch went to an empty desktop and the front app's window got hidden), it is not raised: raising a hidden window made macOS jump back to the desktop that has it, and the two displays went back and forth.
- Displays that do not have a desktop with that number, and displays showing a full-screen app, are left alone. Creating desktops automatically, and merging paired desktops when a display is removed, were not done because there is no public API (SIP blocks the private function that moves windows to another desktop).
- Following takes about 0.3s longer (the switch animation on the other display). The user accepted this.

## Drips from bottom corners

Side streams come down winding left and right irregularly like a snake (sometimes slightly crossing into the window). Then they go around the bottom corner curve up to 65° and get thinner (`WaterSimulation.dripAngle`, shader `kDripAngle`). The head does not stop at the end of the side. It also follows the curve down (`cornerRun` = R × 65° × 1.25; the shader draws only up to the curve progress `headProg`). Before, the curved part appeared all at once, which was noticeable on widgets with large corners and short height. A drop forms at the end and grows. When it is full, it falls at the same position and size. The amount that falls is sensitive to the flow rate, but there is a minimum interval between drops from one stream (about 0.11~0.18s). Water that collects in between makes the next drop bigger (this prevents a dense line of drops). Falling water gets an initial horizontal velocity that slowly sways left and right (`sway`), so at first it curves along x ∝ √y. From about 60pt down, each drop drifts sideways in its own way (`Drip.wander`). A falling drop inherits the horizontal speed the window was moving at that moment. (We also tried pouring it as a water column, a thin string, or a continuous stream, but it looked like a faucet or an icicle, so we took it out.)
